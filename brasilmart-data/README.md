# BrasilMart data preparation

This folder is ready to put in a Git repository. It contains a reproducible Python 3.11+ preprocessing script, a small source-backed demo export, table templates, and validation evidence. It uses only Python's standard library. The nine raw Olist CSVs stay outside this folder. The data comes from the [Olist Brazilian E-Commerce Public Dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), which is anonymised historical commercial data with a CC BY-NC-SA 4.0 license. Use the derivative data within the training exercise and check the license before any broader distribution.

## What we completed

We processed six Olist CSVs into relational staging tables for the BrasilMart support agent. The script joins orders to customers using `customer_id`, keeps `customer_unique_id` as the stable repeat-buyer key, joins items and payments by `order_id`, translates available product categories, and sums payment rows using decimal arithmetic. Source order statuses, timestamps, IDs, and item/payment amounts remain traceable to the original rows. No order fact is generated by AI.

The checked-in `demo/` export has **9 customers, 30 orders, 34 items, and 31 payment rows**. It includes two distinct repeat buyers for customer-isolation tests and source-backed orders for day-14 and day-15 return decisions, late delivery, open overdue delivery, cancellation, and a missing delivery date. The `--mode full` run also completed locally and produced **96,096 customers, 99,441 orders, 112,650 items, and 103,886 payment rows** in the Git-ignored `output/` folder.

Validation found **8 orders marked delivered without an actual delivery timestamp, 775 orders without item rows, and 1 order without a payment row** in the full source. These are reported in `demo/exceptions.csv` and `demo/validation_report.json`. Missing values stay missing; a flagged delivered order cannot receive an automated lateness or return decision. Six automated checks passed, and all 30 exported orders, 34 items, and 31 payments were cross-checked against the raw CSVs.

The database relationship is `CustomerIdentity -> Customer -> Order -> {OrderItem, OrderPayment}`. `CustomerIdentity` is a separate mapping to authenticated Teams users and is **not populated with real identities in Git**. `ReturnRequest`, `Complaint`, and `SupportCase` are empty table templates for records the agent will create later.

## Run it

With the six required Olist CSVs in the parent `archive` folder:

```powershell
python .\brasilmart-data\preprocess.py --source-dir . --output-dir .\brasilmart-data\demo --mode demo
```

For a complete local export, write into the ignored `output` folder:

```powershell
python .\brasilmart-data\preprocess.py --source-dir . --output-dir .\brasilmart-data\output --mode full
```

The six input files are `olist_customers_dataset.csv`, `olist_orders_dataset.csv`, `olist_order_items_dataset.csv`, `olist_order_payments_dataset.csv`, `olist_products_dataset.csv`, and `product_category_name_translation.csv`. The reviews, sellers, and geolocation files are deliberately unused. Input checksums and row counts are in `demo/validation_report.json`. The batch ID is stable for the same inputs, mode, date, and return window.

Run verification with:

```powershell
python -m unittest discover -s .\brasilmart-data\tests -v
```

## Output tables

| CSV | Purpose | Unique key / relationship |
| --- | --- | --- |
| `customers.csv` | One record per Olist repeat-buyer identity; city/state only | `customer_unique_id` |
| `orders.csv` | Exact Olist recorded status and timestamps, plus payment aggregate and quality flags | `order_id`; `customer_unique_id` → customers |
| `order_items.csv` | Item, category, BRL item price and freight | `(order_id, order_item_id)` → orders |
| `order_payments.csv` | Original payment rows | `(order_id, payment_sequential)` → orders |
| `import_batches.csv` | Stable import batch ID and source-manifest digest | `import_batch_id` |
| `demo_config.csv` | Business date, return window, policy version, dataset notice | `setting_name` |
| `customer_identity_template.csv` | Persona-to-Olist-customer plan; **not an authentication import** until filled locally | Assign `tenant_id` and authenticated `User.Id` in the training tenant. Leave the committed file blank. |
| `return_requests_template.csv`, `complaints_template.csv`, `support_cases_template.csv` | Headers for empty operational Dataverse tables | Create these tables in Dataverse. The agent flows write actual records. |
| `exceptions.csv` | Whole-source anomalies with disposition | Use for review; `loaded_flagged` rows remain in orders with restricted decisions. |
| `fixture_manifest.json` | Exact demo scenario IDs and expected outcomes | Demo mode only. |
| `validation_report.json` | Input checksums, row counts, status counts, anomaly counts | Validation evidence. |

The output CSVs are **staging data**, not a Dataverse solution package. Use the publisher prefix required by your environment when creating custom tables. Create/import in this order: `ImportBatch`, `Customer`, `Order`, `OrderItem`, `OrderPayment`, then `DemoConfig`. Add `CustomerIdentity` only after the authenticated Teams users are known. Create `ReturnRequest`, `Complaint`, and `SupportCase` as empty operational tables with the template columns; these receive records from flows. If importing via Dataverse dataflows, map the source IDs to alternate keys and the foreign-key columns to lookups. Preserve source timestamps as text or as **time zone independent** values; a user-local Dataverse DateTime conversion can change a displayed Olist date. Store BRL values as decimal with two places, not floating point.

For the authenticated mapping, copy `demo/customer_identity_template.csv` to `identity.local.csv` and fill `tenant_id` and the agent's authenticated `User.Id` values. Keep that local file out of Git. The two priority rows are `USER_A` and `USER_B`; each maps to a different Olist customer. Other persona rows support boundary and anomaly tests if additional Teams test users are available. A user-provided name, email, customer ID, or order ID must never create or alter a mapping. See [Dataverse mapping](DATAVERSE_MAPPING.md) for the flow checks.

## Exactness and demo-date rules

The demo business date is **2018-09-01**, while `order_status` is the value recorded in the Olist export. This is a simulation date, **not a source snapshot timestamp**. The script chooses demo orders with no recorded milestone after 2018-09-01, but Olist does not give enough event history to prove when all status changes happened. Say “recorded dataset status,” and label lateness “as of the demo date.” Never present these as live 2026 orders.

Raw order timestamps are preserved exactly as text. Comparisons use the `YYYY-MM-DD` date component without timezone conversion. `recorded_payment_total_brl` is the decimal sum of source payment rows; a missing payment remains blank. The script does not invent product names, tracking events, refunds, or complaints. An order marked `delivered` without an actual delivery timestamp is loaded with a quality flag; automated lateness and return decisions must stop and offer support.

The `fixture_manifest.json` lists two repeat buyers and source-backed cases for return day 14, day 15, open overdue, delivered late, on-time delivery, canceled/unavailable, and missing delivery date. The demo export contains **30 orders, 34 items, 31 payment rows, and 9 customers**. All selected order facts came from the six Olist CSVs; the return policy, complaint priority, identities, and support records are BrasilMart training configuration.

## Flow boundary

Every order-related flow takes authenticated `User.Id` and resolves it through `CustomerIdentity` before any `Order` lookup. After resolving, filter by both requested `order_id` and mapped `customer_unique_id`. Repeat that check before a return, complaint, or support-case write. Never expose `customers.csv`, `orders.csv`, or `fixture_manifest.json` as generative knowledge. Only authored policy files belong in knowledge.
