# Dataverse table mapping

These CSVs are staging files. Create custom tables with your environment's publisher prefix, then map each CSV column to a same-purpose field. The source IDs are stable text keys; use Dataverse alternate keys where shown. Standard Dataverse row IDs can remain autogenerated.

## Import order and relationships

| Step | Table / CSV | Alternate key | Lookup |
| --- | --- | --- | --- |
| 1 | `ImportBatch` / `import_batches.csv` | `import_batch_id` | None |
| 2 | `Customer` / `customers.csv` | `customer_unique_id` | None |
| 3 | `Order` / `orders.csv` | `order_id` | `customer_unique_id` → Customer; `import_batch_id` → ImportBatch |
| 4 | `OrderItem` / `order_items.csv` | `order_id` + `order_item_id` | `order_id` → Order; `import_batch_id` → ImportBatch |
| 5 | `OrderPayment` / `order_payments.csv` | `order_id` + `payment_sequential` | `order_id` → Order; `import_batch_id` → ImportBatch |
| 6 | `DemoConfig` / `demo_config.csv` | `setting_name` | None |
| 7 | `CustomerIdentity` / provision locally | `tenant_id` + `authenticated_user_id` | `customer_unique_id` → Customer |

Create `ReturnRequest`, `Complaint`, and `SupportCase` with the corresponding template header fields. The templates contain no operational records. Link their `order_id`, `order_item_id`, `return_request_id`, and `complaint_id` to source/operational rows as appropriate. The write flows should populate their autogenerated record IDs and `created_at` values.

## Field types

- All Olist IDs, tenant IDs, authenticated user IDs, status/category values, source notices, quality flags, and free-text descriptions: **Text**. Use at least 255 characters for authenticated user ID; allow longer text for issue summaries and complaint descriptions.
- `order_purchase_timestamp`, `order_approved_at`, `order_delivered_carrier_date`, `order_delivered_customer_date`, `order_estimated_delivery_date`, and `shipping_limit_date`: preserve as **Text** in exact Olist `YYYY-MM-DD HH:MM:SS` format. A parallel time-zone-independent DateTime field is optional, but do not replace the source text. For policy comparisons, parse the first ten characters as a date in the flow.
- `price_brl`, `freight_value_brl`, `payment_value_brl`, and `recorded_payment_total_brl`: **Decimal**, two fractional digits, BRL. A blank aggregate stays null.
- `order_item_id`, `payment_sequential`, `payment_installments`, `payment_row_count`, and `return_window_days`: **Whole number** where used operationally. CSV keys contain numeric text, which Dataverse can map to these fields.
- `enabled`: **Yes/No**. Never import the committed identity template with empty IDs as enabled users.
- `business_date` in `ImportBatch`: **Date only**; `DemoConfig.setting_value` remains text because the table contains mixed setting types.
- `requested_date`: **Date only**; `created_at`: **Date and time, time zone independent or UTC with documented conversion**. These are new operational records, unlike the historical Olist source timestamps.

## Required backend behavior

Resolve the authenticated `User.Id` together with tenant ID to exactly one enabled `CustomerIdentity`. Every read that returns order fields filters `Order.order_id` and `Order.customer_unique_id` together. Every order-linked write repeats this check inside the flow immediately before creating a row. A typed order ID, card selection, or user-provided customer identifier is only an input to check, never proof of ownership. `CustomerIdentity` is intentionally absent from the generated data export until the training tenant's identities are known.

`ReturnRequest` records both accepted and refused decisions. Use `idempotency_key` as a unique key for retries. Also query for an active request for the same item before creating a new one. `Complaint` priority is set in the flow from structured reason and order facts. `SupportCase` is written before a Teams notification; `notification_state` records whether that post succeeded. The support team should query these tables directly; the bot's generated answer is not the record of truth.
